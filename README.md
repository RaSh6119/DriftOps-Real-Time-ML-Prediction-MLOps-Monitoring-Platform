# DriftOps

A production-style ML system that predicts flight delays and monitors itself in production — real data, explainable predictions, drift detection, and a self-correcting retraining pipeline, not just a notebook that stops at `model.fit()`.

## What it does

- Predicts the probability a flight will be delayed and by how many minutes, given origin, destination, carrier, distance, and scheduled time.
- Explains every prediction with SHAP-based feature attribution ("departing from ATL increased risk by 40%").
- Tracks every training run in MLflow's experiment tracker and model registry, with full version history.
- Detects data drift between the training distribution and current data using a Population Stability Index (PSI) score per feature.
- Automatically compares a retrained candidate model against the current production model and only promotes it if it's genuinely better — never deploys a non-improving retrain.
- Ships a React + TypeScript dashboard for both the product experience (prediction UI) and the MLOps experience (live serving stats, model version history, drift report, one-click retrain trigger).

## Architecture

```
React + TypeScript Dashboard (Vite, Tailwind, Recharts)
        |
        v
FastAPI Backend
        |
        |---- POST /predict         prediction + SHAP explanation
        |---- GET  /model-info      current model version, metrics
        |---- GET  /model-metrics   live serving stats + accuracy history
        |---- GET  /drift-report    PSI drift score per feature
        |---- POST /retrain         train candidate, promote if better
        |---- GET  /health
        |
        v
Model Serving Layer
        |
        |---- Model bundle exported from MLflow registry (joblib)
        |---- Shared preprocessing pipeline (scikit-learn ColumnTransformer)
        |---- Lightweight "feature store": historical aggregate lookup
        |     tables persisted alongside the model, so the API accepts
        |     only what a real user would know (origin, destination,
        |     carrier, time) and reconstructs engineered features itself
        |
        v
MLOps Layer
        |
        |---- MLflow: experiment tracking + model registry (SQLite-backed)
        |---- PSI-based drift detection (+ optional Evidently AI HTML report)
        |---- Docker + docker-compose
        |---- GitHub Actions CI (lint + smoke test, both frontend and backend)
```

## Tech stack

**ML:** XGBoost (classifier + regressor), scikit-learn preprocessing, SHAP explainability, MLflow experiment tracking and model registry

**Backend:** FastAPI, Pydantic, joblib

**Frontend:** React, TypeScript, Vite, Tailwind CSS v4, Recharts

**MLOps:** MLflow, PSI drift detection (self-implemented; Evidently AI used for a supplementary visual report), Docker, GitHub Actions

**Data:** US DOT / Bureau of Transportation Statistics Reporting Carrier On-Time Performance data — real flight records, not synthetic

## Setup

### 1. Get the data

Download flight on-time performance data from the [BTS TranStats download tool](https://www.transtats.bts.gov/DL_SelectFields.aspx?gnoyr_VQ=FGJ&QO_fu146_anzr=b0-gvzr) ("Reporting Carrier On-Time Performance"). Select one month to start, and include at minimum: `Year, Month, DayOfWeek, FlightDate, Reporting_Airline, Origin, Dest, CRSDepTime, DepDelay, CRSArrTime, ArrDelay, Cancelled, Diverted, Distance, WeatherDelay`. Save the CSV to `data/raw/`.

### 2. Backend

```bash
python -m venv .venv
.venv\Scripts\activate        # or source .venv/bin/activate on macOS/Linux
pip install -r requirements.txt

python ml/data_prep.py         # clean, split, engineer features
python ml/train.py             # train + register the model in MLflow

cd backend/app
uvicorn main:app --reload --port 8000
```

### 3. Frontend

```bash
cd frontend
npm install
npm run dev
```

Open `http://localhost:5173`.

### Or, run everything in Docker

```bash
docker compose up --build
```

Same ports as above — no code changes needed either way.

## Design decisions worth knowing

A few choices were deliberate, not oversights:

- **No Feast, Kubernetes, Helm, or Terraform.** A feature store and container orchestration solve problems this project's scale doesn't have. A lightweight, self-persisted lookup-table "feature store" and Docker Compose cover the actual need without adding unused complexity.
- **Real data, not synthetic.** Training data is genuine US flight records with real messiness (missing values, class imbalance, small-sample noise in engineered features), not a generator that encodes its own answer.
- **PSI computed independently, not parsed from Evidently AI's internals.** Evidently's API has changed shape across major versions; the structured `/drift-report` response depends on a self-contained, stable PSI implementation instead. Evidently is still used for a supplementary HTML report, isolated so its failure can't break the core endpoint.
- **Retraining only promotes a model that's demonstrably better.** Every retrain registers a new MLflow version for audit history, but only updates the served model if its ROC-AUC beats the current production version — avoiding unnecessary model churn.

The full build log — every step, every design decision with its reasoning, and every bug encountered and fixed along the way (including a genuinely subtle sparse-vs-dense input bug that caused SHAP explanations to describe the wrong prediction) — is in [`DECISIONS.md`](./DECISIONS.md).

## Known limitations

- Training data currently covers a single month, so seasonal patterns are limited and the "current production model" hasn't yet been tested against genuinely new data (every retrain so far has used identical data, correctly resulting in no promotion).
- Live prediction/latency stats are stored in-memory and reset on server restart — fine for a single-instance deployment, would need a shared store (DB/Redis) for multi-instance production use.
- `weather_severity` and related engineered features are historical aggregates, not real-time weather data.
